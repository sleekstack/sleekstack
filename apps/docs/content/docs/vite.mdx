---
title: Vite plugin
description: One plugin for ui JSX, analyzer diagnostics, stable component ids, file-based routes and client and SSR bundles.
---

`@sleekstack/ui-vite` sets up a Vite app on `@sleekstack/ui` in one line: `plugins: [sleekstack(options)]`. Add `@vitejs/plugin-react` beside it when the app has React Guests. It is a plugin, not a meta-framework. `apps/playground/ui` in the repository is a working example: a file-routed app rendered by `handle`, prerendered by `vite build` and hydrated by `startRouter`.

## Options

Every option is optional.

| Option                | Default      | What it does                                                                                                                                                                                                                                |
| --------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `include` / `exclude` | none         | Globs (relative to the Vite root) or regexes of `.jsx` / `.tsx` files that are ui JSX without the pragma. A file that already names a `@jsxImportSource` keeps it.                                                                          |
| `routesDir`           | `src/routes` | Directory of route files, relative to the Vite root. Serves `virtual:sleekstack/routes`.                                                                                                                                                    |
| `entries`             | none         | `{ client, server }`, paths relative to the Vite root. `vite build` writes `dist/client` and `dist/server`, and the dev server answers every request through the server entry.                                                              |
| `hmr`                 | `true`       | Dev only. A ui module whose exports are all components hot-updates and keeps its `useLocal` state; a ui module that exports anything else reloads the page. React guests are untouched (Fast Refresh owns them). `false` emits no HMR code. |

## The pragma rule

ui JSX is opt-in per file ([ADR 0015](https://github.com/sleekstack/sleekstack/blob/master/docs/adr/0015-host-first-component-framework.md)). The plugin sets no global `jsxImportSource`:

- A file whose first line is `/** @jsxImportSource @sleekstack/ui */` compiles as ui JSX. Vite reads the pragma only in the comments before the first statement. After an `import`, it is plain text and the file compiles as React JSX.
- A file matched by `include` and not by `exclude` gets the pragma added on line 1.
- Any other file keeps the default, which is React JSX for Guests. ui files and React files can sit side by side in one app.

## Analyzer diagnostics

The plugin runs the `sleekstack check` analysis over the Vite root's `tsconfig.json`. On `vite build`, an analyzer error fails the build with its file:line. In dev, the analyzer runs after source changes, with a debounce. Errors show in Vite's error overlay, and the overlay clears once the code is fixed. A crash inside the analyzer is reported and never stops the dev server. A run is whole-program TypeScript, so the dev server pauses while it runs.

The analyzer reads a router's `pages` written as an object literal, or imported from `virtual:sleekstack/routes`: it finds each route file through `routes.gen.d.ts` and reports a missing service at the route file's line. A declaration that disagrees with the route files is reported, never guessed; run `vite` to rewrite it.

## Stable component ids

Each function that a ui JSX file exports gets a stable id, `<path from the Vite root>#<export name>`, in place of the load-order counter. A re-export keeps the id, and so does a re-evaluation of the module. Two files that would give the same id fail the build. Only functions written in the export get an id: a declaration, an arrow function or a function expression. Without the plugin, ids still work through the counter.

## Hot updates

In dev, a ui module whose value exports are all functions written in place registers them with `acceptUpdate` and accepts its own updates, so editing a component re-runs its live instances with their state and focus. A ui module that also exports a constant, a class or a re-export reloads the page, and so does an edit to a non-component file such as a helper that such a module imports. Files without the ui pragma, such as React guests, get no HMR code. Production builds never carry it. Set `hmr: false` to turn it off in dev.

## File-based routes

Files under `routesDir` become a [router](/docs/routing) app ([ADR 0050](https://github.com/sleekstack/sleekstack/blob/master/docs/adr/0050-file-routes-layouts-and-lazy-pages.md)). A file's path without its extension is its route name:

- `users/[id].tsx` is `/users/:id`, and an `index` file is its directory's path.
- `posts/[[page]].tsx` is the optional `/posts/:page?`, matching `/posts` and `/posts/2`. `guide/[...slug].tsx` is the splat `/guide/*slug`, matching `/guide/a/b` but not `/guide`. Optional and splat segments must be last.
- A `(group)` directory adds no path segment. A file or directory whose name starts with `_` is not a route, so helpers, components and tests can sit beside the routes; `_layout` files and a root `_notFound` have the roles below.
- At one position a static segment matches first, then a param, then an optional param, then a splat. Two files with one path, a bad segment, a misplaced optional or splat, and a file with no default export fail with the file's path.

A route file is a whole page: its default export is the component, and its `loaders`, `fallback` and `prerender` exports are the rest of the page. `virtual:sleekstack/routes` exports `table`, `pages` and, when a root `_notFound` file exists, `notFound`, so the app is `router({ table, pages, notFound })` with all three imported from the module, and `sleekstack check` reads it as it reads a hand-written router.

A `_layout` file's default export takes `children` and wraps every page in its directory and below, outer layouts first; inside a `(group)` it wraps only the group. Its `loaders` run with the page's, layouts' first, each loader once, so a layout guard that redirects redirects every page below it. Layouts are composed when the module is generated, so they remount on every navigation as the page does. `notFound` gets no layout, because the router runs no loaders for the not-found page.

In the client build each page is its own chunk, loaded once on its first navigation (the first page before hydrating); SSR and prerender import every page up front. A failed load renders a `LazyLoadError` at the nearest `Boundary` and is tried again on the next navigation. To hide the code-then-data wait, pass the page's `load` to `Link`'s `code`: `code={pages['users/[id]'].load}`.

For TypeScript, the plugin writes a types-only `routes.gen.d.ts` into `routesDir` ([ADR 0045](https://github.com/sleekstack/sleekstack/blob/master/docs/adr/0045-vite-plugin-route-declaration.md)). The route table itself is never generated. In dev, adding, removing or renaming a route, layout or `_notFound` file rewrites it and reloads the page. Commit the file, or gitignore it and run `vite` once before a plain `tsc` or `vite build`.

## Client and SSR entries

With `entries`, `vite build` builds the client bundle and then the server bundle. The server entry's default export takes a `Request` and returns a `Response`, for example `handle` from `@sleekstack/router` with `stream: true`. It imports `scripts` from `virtual:sleekstack/client` and puts it in the document head. In a build, `scripts` loads the built client chunk and its CSS. In dev, it loads the source entry with HMR.

`virtual:sleekstack/client` has no generated declaration. Declare it in the app with `declare module 'virtual:sleekstack/client' { export const scripts: string }`, as `apps/playground/ui/src/env.d.ts` does. `vite build --watch` is not supported with `entries`.

## Known limitations

- With `entries`, use an absolute `base` (the default `/`, or a path such as `/app/`). A relative base such as `./` is rejected, because a nested route like `/users/42` would request its scripts and CSS from the wrong path.
- `prerender()` and `prerender: true` expand only `:param` routes. List the paths of optional and splat routes in `prerender`.
- No deploy adapters yet.
