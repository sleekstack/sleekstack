title: Queries
description: Cached server reads and mutations on the native atom store.

`@sleekstack/query` caches async reads by key, like TanStack Query, but a query is an Effect. Its services are Tags from the nearest query store's scope, its failures are typed, and its cache lives in that store, so it ends with the scope. There is no second client or runtime. Coming from TanStack Query? See [TanStack Query mapping](/docs/tanstack-query).

The query store is the `AtomStore` of the root `LayerProvider`. Nested providers share it. Wrap a subtree in `QueryProvider` to use the nearest `LayerProvider`'s store instead, so its queries can `yield*` that provider's Tags.

## kit

`cachedQuery` and `mutation` come from `@sleekstack/kit`; `useQuery`, `useMutation`, `useQueryClient` and `QueryProvider` come from `@sleekstack/kit/react`. They are named apart from the server-side `query` / `defineQuery` of `@sleekstack/kit/next`, which run once per request and cache nothing.

- `useQuery` never suspends on the client: check `isPending`. A failure comes back as `error` (a `SleekStackError`), with any earlier `data` kept.
- `staleTime` and `gcTime` are milliseconds; `retry` is a number of retries.
- `mutate` resolves with the value or rejects with a `SleekStackError`. `useQueryClient()` gives `invalidate`, `refetch`, `setData` and `getData`.
- A key that is not serializable throws `SleekStackError` with code `InvalidQueryKey`.
- `@sleekstack/kit` depends on `@sleekstack/query`.

## Effect-native

`Query.make`, `Mutation.make` and the `Queries` service come from `@sleekstack/query`. The hooks (`useQuery`, `useQuerySuspense`, `useInfiniteQuery`, `useMutation`, `useQueries`, `QueryProvider`) come from `@sleekstack/react`.

<include>../../snippets/queries-effect.tsx</include>

- `key` returns a serializable tuple. Equal keys (compared as canonical JSON, with sorted object keys) share one entry; a non-serializable key throws `InvalidQueryKey`.
- `staleTime` (default 0) gates a new observer's refetch and `refetchOn` sources; a hydrated entry is fresh until it passes. A mounted entry never refetches by itself. `invalidate`, `refetch` and `refetchInterval` ignore it.
- `gcTime` (default 5 minutes) is the idle time before an unobserved entry is removed. An in-flight fetch is interrupted when it is removed.
- `retry` is a `Schedule`. It re-runs typed failures only, never defects or interruption.
- `useQueries()` returns the `Queries` client: `invalidate`, `refetch`, `cancel` and `reset` take a query atom or a filter `{ prefix, predicate }` (none: every query); `setData`, `updateData` and `getData` take one query atom.
- `useQuerySuspense` suspends only while there is no value. A failure after a value returns the stale `data` with the `error`.
- `Query.infinite` keeps pages in one entry; `useInfiniteQuery` adds `fetchNext` and `fetchPrevious`.
- `Query.select` maps fetched data with an Effect (for example `Model.fromDto`) and memoizes it on the data.
- A mutation's state and concurrency are per hook by default; `Mutation.shared` shares them per store. `concurrency` is `parallel` (default), `queue` or `switch`. Overlapping optimistic writes roll back in reverse order. A successful refetch that lands while optimistic writes are pending becomes their new base: the writes are re-applied over it, and a failed mutation rolls back to it rather than to the stale value. With a hand-provided `Queries` service there is no store to watch, so the refetch is overwritten by the next recompute.

## Build-time checks

`sleekstack check` reads query and mutation fetchers like action bodies: a Tag that no reaching provider gives is a `MissingDependency` at file:line. A key must be a function that returns a tuple literal of literals and its own parameters, like `(id: string) => ['todo', id]`. A parameter typed `any`, `unknown` or a union (string-literal unions such as `'open' | 'closed'` too) fails closed as `Computed`; `boolean` is allowed.

## Devtools

The `@sleekstack/devtools` panel has a Queries tab. `QueryEvents` (from `@sleekstack/query`) keeps a ring of the last 50 events per kind: `added`, `fetching`, `success`, `failure` and `removed`. An interruption is not a failure. The tab also lists the live entries of each store without fetching. Recording is off in production and when `process` is not defined, so the tab is empty there.

## Limits

- `useMutation` returns the idle result in a server render; `mutate` there throws. See [Queries on the server](/docs/queries-ssr#mutations-in-a-server-render).
- An optimistic write is only a value in the cache. An item it adds (for example a new task with a temporary id) is not on the server until the refetch replaces it; the showcases do not let users select such an item.
- `gcTime` is per query definition, not per key.
- Server rendering with prefetch (core and kit) is in [Queries on the server](/docs/queries-ssr).
