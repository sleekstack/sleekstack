A Controller is a `*.controller.ts` file under `server/routes` ([ADR 0053](https://github.com/sleekstack/sleekstack/blob/master/docs/adr/0053-file-routed-controllers.md)). Its path sets its URL, and each exported HTTP method answers requests from decoded input. Nothing registers it: the `serverServices()` plugin of `@sleekstack/ui-vite` (also part of `sleekstack()`) finds it, and `start()` serves it. There is no wrapper function around a method. The written-out signature is the contract, and the input Schemas are read from it.

The same plugin finds the rest of the server ([ADR 0054](https://github.com/sleekstack/sleekstack/blob/master/docs/adr/0054-server-auto-wiring.md)): [Layer Files](#layer-files) provide the services, the [Server Root](#the-server-root) holds the error sink, and [RPC Files](#rpc-files) and the [RPC Manifest](#the-rpc-manifest) define the Server Services that pages call. A server entry lists none of them.

The [realworld app](https://github.com/sleekstack/sleekstack/tree/master/apps/realworld/server) is the worked example: its whole REST facade is a `_defaults.ts` and 14 Controllers under `server/routes/api`, its infra is three Layer Files, and its pages call three RPC Files.

## Files and URLs

A file's path under `server/routes`, without `.controller.ts`, is its route name, and it sets the URL with the [file route](/docs/vite) syntax of pages:

- `notes.controller.ts` is `/notes`, and `notes/[id].controller.ts` is `/notes/:id`. An `index` file is its directory's path.
- `[[page]]` is an optional param and `[...rest]` a splat, matching one or more segments. Either must be the last segment. A splat does not match its own directory, so `/api` itself needs an `index` Controller beside `api/[...rest]`.
- A `(group)` directory adds no segment. A file or directory whose name starts with `_` is not a route.
- At one position a static segment matches first, then a param, then an optional param, then a splat. A trailing slash is ignored, and a path with an empty segment (`/api//x`) matches no Controller.

A request goes to middleware, then server functions and Server Service methods, then a `start({ handlers })` entry at its exact pathname, then the first matching Controller, then the page router. A Controller whose pattern also matches a page's URL, such as a splat, shadows that page: it serves its own methods there and answers 405 for the rest, with no fall-through to the page.

These fail the load of the discovered app, naming the files: an optional or splat segment that is not last, two Controllers at one path (param names are ignored), a Controller at a page route's path, a Controller whose URL would start with `/_sleek/`, and a `*.controller.ts` under the server directory but outside `server/routes`.

## Methods

A method is a named export `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE` or `OPTIONS`. It takes one input object, `{ params?, query?, body? }`, or none, and returns an `Effect.Effect<A, E, R>`.

Before the method runs, `params` is decoded from the path, `query` from the URL and `body` from JSON:

- A type written `Schema.Schema.Type<typeof X>`, where `X` is an exported Schema of a client-safe module, uses `X` itself. It may stand inline or behind a type alias of the same file, as a property, an array element or a union member.
- Any other type is printed to a Schema from the [Server Service](/docs/server-services) type subset. A plain annotation is exactly as strict as its type: `title: string` accepts the empty string, so a constraint needs a referenced Schema.
- Path and query values are strings. A printed `number` accepts a finite decimal only, and a printed `boolean` accepts `true` and `false` only. A referenced Schema for `params` or `query` must encode to strings.
- A repeated query key gives an array when the type is an array, else its last value. `[[id]]` is an optional string, and a splat is one string joined with `/`. Keys the type does not name are ignored.
- The keys of `params` equal the path's params. A method on `notes/[id]` without `params: { id }` is `ControllerParamsMismatch`.
- `body` is legal on `POST`, `PUT`, `PATCH` and `DELETE`. A method that declares it needs `Content-Type: application/json` (a charset is accepted), and an empty body fails the decode. A method that declares no `body` leaves the body unread and may read it through `Request`.

`sleekstack check` and the Vite plugin report a method they cannot read as `ControllerMethodShape`, with file:line. A near-miss export (`get`, `Post`, a default export) is one, and so is an Effect return type written through a type alias. Write `Effect.Effect<A, E, R>` inline and alias only the success value. See [Errors](/docs/errors#controller-errors).

## Answers

- A value answers as JSON with 200. With a written success type, the value is encoded through its Schema, so fields outside it are not sent. Without one, the value is serialized as it is.
- `void` answers 204, and `null` answers JSON `null`. `undefined` sends an empty body at any status. The statuses 204, 205 and 304 never carry a body.
- A method with no written success type may return a `Response`, which passes through with its own status and body.
- The method shapes the answer through the request services `Request`, `Cookies`, `ResponseHeaders` and `ResponseStatus`, provided per call. `yield* ResponseStatus.set(201)` sets the status. A value that is not an integer from 200 to 599 is a defect, `InvalidStatus`.
- When a method fails, its status is dropped and the answer is whatever `wrap` gives the failure. Staged `ResponseHeaders` and `Set-Cookie` lines still apply to it.

`HEAD` runs `GET` and drops the body unless the file exports `HEAD`. `OPTIONS` answers 204 with `Allow` unless the file exports it. No CORS headers are sent; set them in `wrap` through `ResponseHeaders`.

## Failures and `wrap`

One call checks, in order: the method, the path's escapes, the content type, the body size, the JSON, then the decode of `params`, `query` and `body` with all issues reported. Each failure reaches the `wrap` chain. One that no `wrap` handles gets its default answer:

| Failure                | When                                                                      | Unhandled                       |
| ---------------------- | ------------------------------------------------------------------------- | ------------------------------- |
| `MethodNotAllowed`     | The path has no such method. It carries `allowed`.                        | 405 with `Allow`                |
| `InvalidPathEncoding`  | A param or splat value has a malformed percent-escape.                    | 404, no body                    |
| `UnsupportedMediaType` | A method that declares `body` got no `Content-Type: application/json`.    | 415                             |
| `BodyTooLarge`         | The body is over `bodyLimit`.                                             | 413                             |
| `ParseError`           | Malformed JSON (`is not valid JSON`), a missing body, or a failed decode. | 400 with the `DecodeError` JSON |
| anything else          | The method's own errors, an encode failure or a defect.                   | the error sink, an empty 500    |

A `ParseError`'s issue paths start at the input part: `params.id`, `query.limit` or `body.title`. A malformed escape in a static segment matches no Controller and falls through to the page router. A `Redirect` or `NotFound` from `@sleekstack/router` that no `wrap` handles answers 302 or 404.

A `wrap` export takes `(next, request)`, where `next` is decode, method and encode, and returns the answer. It provides services, such as the viewer, and maps failures to responses. A `_defaults.ts` file, the Directory Defaults, gives its `wrap` to every Controller in its directory and below:

<include>../../snippets/controllers/server/routes/_defaults.ts</include>

- The chain runs outer first: each `_defaults.ts` from the server directory down, then the Controller's own `wrap`. The chain starts at the server directory, so Controllers outside it have no Directory Defaults.
- `sleekstack check` reads the services a `wrap` provides from its written signature: those in `next`'s requirements that its result leaves out. A `wrap: Wrap` annotation provides nothing to the check, so write the signature out.
- `bodyLimit` (bytes, a positive integer) applies only to a method that declares `body`. The Controller's own export wins, then the nearest `_defaults.ts`, then `start({ bodyLimit })`, then 1 MiB.
- `origins` in a Controller or `_defaults.ts` only adds to the allow-list of the server-function wire. No file can remove an origin. A Controller has no origin check of its own: its `application/json` rule stops cross-site form posts.
- A `bodyLimit` export that is not a positive integer, or an `origins` export with an entry that is not a bare origin (`InvalidOrigin`), fails the app's load on its first request, naming the file.

## Serving

`start()` reads the discovered app on its first request. Explicit options merge with it: the given `controllers` are matched after the discovered ones, a `services` entry whose Tag is already listed registers nothing, and `bodyLimit` and `onError` are the app-wide defaults. Without a `router` option, pages come from the discovered page router, and with neither every page answers 404.

<include>../../snippets/controllers/server/app.ts</include>

A method's `R` comes from a [Layer File](#layer-files), `start({ layer })`, a `wrap`, or the request services. The services are ordinary Tags and Layers: here `Notes` comes from the Layer File `notes.layer.ts` and `Viewer` from the directory `wrap`.

<include>../../snippets/controllers/server/notes.ts</include>

`sleekstack check` counts every Controller as a root, so a service no one provides is a `MissingDependency` with file:line, even in an app with no ui. `start()` with no options and no discovered app fails every request, naming the missing plugin. Auto-wiring needs Vite; a host without it passes the options itself.

The [Vite plugin](/docs/vite#controllers-and-the-discovered-app) page covers the discovery options, dev reloads and how a dev server forwards Controller paths to `start`.

## Layer Files

A `*.layer.ts` file whose default export is a Layer is a Layer File. The plugin finds every one in the app's TypeScript program except tests (`__tests__/`, `test/` and `tests/` directories, `*.test.*` and `*.spec.*` files) and composes them by requirement: a Layer File's requirement is provided by another Layer File's output. The composed Layer serves the Controllers, the generated Server Services and `start({ layer })`.

<include>../../snippets/controllers/server/notes.layer.ts</include>

- One Layer per file, built once for the app. There are no request-scoped Layer Files. Layers compose by Tag, not by instance, so compose a base once rather than re-export it from several Layer Files.
- `start({ layer })` wins for any Tag it provides ([Shadowing](/docs/concepts)) and may itself require what Layer Files provide. An app with nothing left to provide omits `layer`: the option does not accept `Layer.empty`.
- A Layer File that reads `process.env` at the top level reads it at import, so a test sets the variable before importing the app.
- A Layer File whose build fails fails the first request with the build's cause, and every later request the same way. The app is never served half-built.
- The pass reads the `tsconfig.json` at the Vite root. An app without one composes no Layer Files.

A cycle between Layer Files is `LayerFileCycle`, and two Layer Files that provide one Tag are `LayerFileConflict`, naming both. A requirement nobody provides is `MissingDependency`. A default export that is not a Layer, or is typed `any`, is `ServerFileShape`. Each fails the discovered app's load, naming the file ([Errors](/docs/errors#server-file-errors)).

## RPC Files

A `*.rpc.ts` file under the server directory defines one Server Service with no contract file and no `implement`. Each exported function with a written-out signature is a method, and the build generates its Tag, registry entry, implementation Layer and browser client. The wire id is `<Service>.<method>` at `POST /_sleek/fn/<id>`, the wire of [Server Services](/docs/server-services).

<include>../../snippets/controllers/server/notes-api.rpc.ts</include>

- The Tag is the file's basename without `.rpc.ts` in PascalCase: words split at `-`, `_` and `.`, each word's first letter capitalised and the rest kept, so `notes-api.rpc.ts` is `NotesApi`. `export const service = 'Notes'` overrides it with a string literal. Either must match `[A-Za-z][A-Za-z0-9]*`, else it is `ServerFileShape`.
- A method takes one parameter of any written type, or none, and returns a written `Effect.Effect<A, E, R>` with no `any`. It is a function declaration, or an arrow or function expression on an exported `const`. Generics, `async` and `Effect.fn` are not read. `export { remove as delete }` names a method `delete`. A non-function export is not a method.
- The types are read as a Controller's are: `Schema.Schema.Type<typeof X>` uses `X`, and any other type is printed from the Server Service subset. `R` may be any service. It must not name another generated Tag.
- `wrap`, `bodyLimit`, `origins` and `service` are options, not methods. `wrap` is an `RpcWrap`, which keeps the method's value and error types: `(next, request) => Effect<A, E, R2>`. It runs inside the generated Layer's methods, so a wire call, a loader's in-process call and `callService` all run inside it. The Controllers' directory `wrap` never reaches an RPC File, while `bodyLimit` and `origins` from a `_defaults.ts` above it do.
- A method that cannot be read is `RpcMethodShape`, with file:line. Tag names from RPC Files, Manifest keys, hand-written `ServerService` ids, Layer File output Tags and `serverFn` ids share one namespace, and a collision is `RpcNameCollision`, naming both ([Errors](/docs/errors#rpc-errors)).

## The RPC Manifest

The server directory's `rpc.ts` exposes chosen Controller Methods as Server Services without redefining them. Its default export is `rpc({ Service: { method: 'VERB route-name' } }, { wrap?, bodyLimit?, origins? })`, of string literals only. A route name is typed from the generated route table, so renaming a Controller is a type error.

<include>../../snippets/controllers/server/rpc.ts</include>

- A wrapped method takes the Controller's input, `{ params?, query?, body? }`, or none when the Controller declares none. It returns the Controller's value as it is, an envelope included. A different shape is an RPC File.
- The RPC face decodes the wire input and runs the method inside the Manifest's own `wrap`, never the Controller's directory `wrap`. Typed errors cross the wire as the method's failure, not as a `Response`, and `ResponseStatus` has no effect. Without a `wrap`, the method's request services still resolve per call.
- A wrapped method must not read the request body, which the wire has already consumed.
- An unknown route, a verb the Controller does not export, or a removed method is `RpcRouteUnknown`. A method that returns a `Response`, has no written signature or uses `any` is `RpcMethodShape`. A default export that is not an object literal of string literals is `ServerFileShape`.

## Calling a generated service

A page or loader imports the Tag from `virtual:sleek/rpc` and calls `yield* NotesApi`. On the server the call runs in process. In the browser, `virtual:sleek/server` carries a client for each generated Tag beside the hand-written ones, so a browser entry changes nothing. Each method also fails with `NetworkError | DecodeError`.

<include>../../snippets/controllers/src/notes-page.ts</include>

The plugin types all of this in `src/server.gen.d.ts`, beside the hand-written Server Services. `virtual:sleek/rpc` declares each generated Tag from its file, and `virtual:sleek/server-app` gains `Controllers` (each route name to its URL pattern), `ControllerModules` (each route name to the type of its module), `GeneratedServices` (each generated Tag by name) and `LayerFileServices` (what each Layer File provides, keyed by its path). Services and methods are sorted, and a stale declaration fails `vite build`.

## Testing

`callController(entry, request, { layer, onError? })` from `@sleekstack/testing` answers a request through the Controller's HTTP face: the method defaults, content type, `bodyLimit`, decode, the `wrap` chain and encode, with a test Layer and no network. It skips middleware and server functions. `entry` is the Controller's entry in the discovered app's `controllers`, because the erased annotations cannot carry its Schemas.

<include>../../snippets/controllers/server/notes.test-example.ts</include>

A URL that the entry's pattern does not match answers 404. A defect answers an empty 500, and its cause goes to `onError`. In a test whose Vitest config has the `serverServices()` plugin, `start` also tries the discovered Controllers first, so a discovered one that matches the same URL answers instead of `entry`.

## The browser boundary

`*.controller.ts`, `*.rpc.ts` and `*.layer.ts` files, and the `_defaults.ts`, `rpc.ts` and `_app.ts` files under the server directory, are server-only. A browser entry (a module importing `virtual:sleek/server` or `virtual:sleek/rpc`) that reaches one fails the client build, naming the import chain, and `sleekstack check` reports `ServerFileInClientGraph`. A page imports the client-safe Schemas a Controller or RPC File references, never the server file. A Schema or error class that a generated client imports must live in a client-safe module, not in the RPC File or Controller itself.
