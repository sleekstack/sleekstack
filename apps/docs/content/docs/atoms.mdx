title: Atoms

An atom is a lazy, reactive value. It is defined once at module level, and its state lives in the `AtomStore` of the mount that reads it, so each mount has its own copy and disposing the mount disposes it. A derived atom reads services from the mount's layer and other atoms through `get`, and recomputes when they change. The design follows [effect-atom](https://github.com/tim-smart/effect-atom), with `AtomStore` in place of its Registry and SleekStack scopes in place of `Atom.runtime`.

## Defining and reading atoms

`@sleekstack/core` has `Atom.make` for values, derived functions, Effects and Streams, and `Result` (`Initial`, `Success`, `Failure`, with a `waiting` flag). In a `@sleekstack/ui` component, `useAtom`, `useAtomValue` and `useSetAtom` read and write them, and an Effect atom's value is its `Result`. A component that reads an atom re-runs when it changes ([UI components](/docs/ui#local-state-and-hooks)).

## SSR and hydration

Atom hooks run during a server render. Opted-in atoms are serialized to a `Snapshot`, and the client seeds its store from it before the first read, so it shows the server values without a hydration mismatch and without re-running seeded Effects.

### Serializable atoms

Only atoms marked with a stable key and a `Schema` cross the wire. Pick a schema whose encoded side is JSON (strings, numbers, booleans, null, arrays, plain objects): the snapshot travels as JSON, so an encoding such as `bigint` breaks the transfer.

<include>../../snippets/atoms-serializable.tsx</include>

- `dehydrate(store)` returns the settled value of every serializable atom built in the store: value-kind atoms always, result-kind atoms only on `Success`. `Initial`, `Failure` and the `waiting` flag are not sent. A value that fails to encode is skipped with a dev warning; a disposed store gives `{}`.
- `hydrate(store, snapshot)` records seeds, and a seeded atom takes its value on first read, before `read` runs: a seeded result atom does not run its Effect until `refresh`. Applying the same snapshot again is a no-op, the first seed for a key wins, a node already built is never overwritten, unknown keys are ignored, an entry that fails its `Schema` decode is dropped with a dev warning (the atom loads normally), and a non-object snapshot counts as empty. `hydrate` never throws. `makeAtomStore({ hydrate: snapshot })` calls it at construction.
- Keys are unique per store: building a second, distinct serializable atom with a key already built in that store throws `DuplicateAtomKey`. In an `Atom.family` callback, build the key from the argument.
- A seeded writable atom uses the seed as its initial value only. A derived atom that is not serializable recomputes on the client from its seeded sources.

### Queries

Query hydration goes through the query cache, not the atom store; see [Queries on the server](/docs/queries-ssr).

### `@sleekstack/ui` host trees: `hydrateMount`

`renderToString` from `@sleekstack/ui` appends a `<script data-sleek-hydrate>` with the store's dehydrated atoms and the layer's query cache. `hydrateMount(app, { layer, container })` reads it, seeds the store before the first run and adopts the server DOM, so each component runs once. A malformed script is reported as `HydratePayloadInvalid` and atoms start from their initial values; a missing script (no state on the server) is not an error.
