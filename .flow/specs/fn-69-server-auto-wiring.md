## Goal & Context
<!-- scope: business -->
<!-- Source-tag breakdown: 15% [user] / 60% [paraphrase] / 25% plan-time decisions (listed in Decision Context) -->

With file-routed Controllers in place (the sibling spec "File-routed Controllers", which this spec depends on), a server still lists its Layers by hand, and each Server Service still takes a contract file, an `implement` call and a `*Live` export. In the user's words: "try total removal of all the wirings only we don't even define the contracts, we only write controllers and the rest will be generated including contracts and wirings".

This spec removes the rest of the wiring. Layer Files are found by extension and composed by what each requires, so a server lists no Layers. An **RPC File** (`*.rpc.ts`) defines a Server Service by its exported functions, with no contract file and no `implement`. An **RPC Manifest** (`rpc.ts` in the server directory) exposes chosen Controller Methods as Server Services "instead of defining manually", and the RPC Files stay for RPC that differs from REST. Realworld and showcase move onto these.

Target: developers who need a typed browser call. Pages keep calling `yield* Comments`, in the browser through a generated client and on the server in-process.

Design record: ADR 0054, building on ADR 0053. Vocabulary: CONTEXT.md (RPC File, RPC Manifest, Layer File, Server Root, Schema File, Server Service).

## Architecture & Data Models
<!-- scope: technical -->

- **Where files are found.** Layer Files: anywhere in the TS program except tests (`__tests__/`, `test/` and `tests/` directories, `*.test.*`, `*.spec.*`). RPC Files and the reserved files `rpc.ts`, `_app.ts` and `_defaults.ts`: under the server directory (the `serverDir` plugin option of the sibling spec, default `server`).
- **Layer composition.** The analyzer reads each Layer File's output and requirements from its type and composes them by requirement (ADR 0011's static graph). The composed Layer also serves the generated implementation Layers and the explicit `layer` option, which wins for any Tag it provides (shadowing, ADR 0003) and may itself require services that Layer Files provide.
- **One signature reader.** Controller Methods (the sibling spec) and RPC File methods are read by the same analyzer reader: a written-out `Effect<A, E, R>`, ADR 0051's type subset plus `Schema.Type<typeof X>` references. It builds the Tag, a registry entry of Schemas, an implementation Layer and the browser client. Wrapped Controller input is read in both variants: a printed `number` is a plain number on the wire, while a referenced Schema is used as written on both faces.
- **Generated implementation Layer.** It captures the non-request services at Layer build (as realworld's `Effect.context<Db | TokenSecret>()` does today) and provides the request services per call; `wrap` and the viewer provision live inside each generated method, so wire calls, loaders and `callService` all get them.
- **Virtual modules.** `virtual:sleek/server-app` is what `start()` reads; `virtual:sleek/rpc` is where pages import generated Tags; the existing `virtual:sleek/server` (browser Layer) and `virtual:sleek/server-registry` also carry the generated services, so a browser entry changes nothing. One Tag object per service is shared by every generated module (showcase compares Tags by identity). The registry is complete (hand-written and generated entries), and `start` de-duplicates `services` by Tag.
- **Two faces of a wrapped Controller Method.** The HTTP face is the sibling spec's. The RPC face decodes the wire input and runs the method inside the Manifest's own `wrap`; it never applies the Controller directory's `wrap`.
- **Wire.** Unchanged from ADR 0039 and the order of checks stays: method, origin, registered id, body size, JSON, input.

## API Contracts
<!-- scope: technical -->

- **Layer File:** `*.layer.ts`, default export a Layer; one per file. Layer Files are app-lifetime only. A Layer File whose output is `never` is still composed.
- **Server Root:** the server directory's `_app.ts`; named export `onError`.
- **RPC File:** `*.rpc.ts` under the server directory. Each exported function with a written-out signature is a method of one Server Service: one parameter of any written type (an object, a scalar, an array, a union) or none, and a written `Effect.Effect<A, E, R>` return. Accepted forms: a function declaration, or an arrow or function expression assigned to an exported `const`, with the parameter and return annotated (a destructured parameter with an inline type counts). Generics, `async` and `Effect.fn` are not supported. `export { remove as delete }` names a method `delete`. A non-function export is not a method. The names `wrap`, `bodyLimit`, `origins` and `service` are options. The Tag name is the file basename without `.rpc.ts` in PascalCase (words split at `-`, `_` and `.`, each word's first letter capitalised, the rest kept so acronyms survive) and must match `[A-Za-z][A-Za-z0-9]*`; `export const service = '<Name>'` overrides it with a string literal of the same shape.
- **RPC `wrap`:** `RpcWrap`, an authoring type exported by `@sleekstack/start`, `(next: Effect<A, E, R>, request: Request) => Effect<A, E, R2>`. An RPC File or the RPC Manifest takes its own `wrap`; the Controller directory `wrap` (which is `Response`-typed) is never inherited by RPC.
- **RPC Manifest:** the server directory's `rpc.ts`; default export an object literal `rpc({ Service: { method: 'VERB route-name' } }, { wrap?, bodyLimit?, origins? })` of string literals. A route name is the sibling spec's route name (a Controller's path under the routes directory without `.controller.ts`, for example `api/articles/[slug]/comments`, `api/index`), typed from the generated route table. The input of a wrapped method is the Controller's `{ params?, query?, body? }`; a method whose Controller declares no input takes none.
- **Pages:** `yield* <Service>` with the Tag imported from `virtual:sleek/rpc`.
- **Wire configuration:** `origins` from every file and the `start` option form one app-wide allow-list (they only add); `bodyLimit` resolves per service by specificity.
- **Diagnostics** (closed `AnalyzeCode` union, each with its table row): `RpcMethodShape`, `RpcRouteUnknown`, `RpcNameCollision`, `LayerFileCycle`, `LayerFileConflict`, `ServerFileShape`; `ServerFileInClientGraph` covers the new server-only kinds.

## Edge Cases & Constraints
<!-- scope: technical -->

- Wrapping never transforms: the RPC method returns the Controller's value as it is, an envelope included. A different shape is an RPC File.
- A Controller Method that returns a `Response`, has no written signature or uses `any` cannot be wrapped.
- Realworld's REST bodies use an envelope (`{article: …}`) but its pages get the bare value, so realworld keeps RPC Files for its pages; the manifest is proven by showcase's `Tally`, whose bare numbers match its REST bodies.
- A Layer File that reads `process.env` at the top level reads it at import, so a test sets the variable before importing the app, as realworld's tests do. A Layer File is composed by Tag, not by instance: apps compose a base once and avoid re-exporting it from several Layer Files.
- `serverFn` stays explicit for explicit Schemas and form actions, because a `serverFn` client stub decodes `formData` and a Server Service client does not.
- A generated Tag name must not equal a hand-written `ServerService` id, a Layer File output Tag key or a `serverFn` id: Context keys are global strings.
- A generated RPC method whose `R` names another generated Tag is not supported (generated Layers are provided by the composed Layer, not part of it).
- A wrapped method must not read the request body: on the wire the body is already consumed. `ResponseStatus` has no effect on RPC calls, and an in-process call from a loader shares the page request's `ResponseHeaders` and cookies.
- A failing Layer File build fails the first request with the build cause and every later request the same way; it never serves a half-built app.
- Layer Files are sorted by path codepoint for a deterministic composed order; services and methods are sorted in the committed declaration, because a stale declaration fails `vite build`.
- Realworld's tests live in `test/`, which the Layer File exclusion covers; a test-only Layer there is never composed into the app.
- `cli/llms.md` has a size cap; this spec adds rows for six new codes, so the generated rows stay one line each.
- Verification follows the repo's verify table for analyzer, `ui-vite`, `start`, `testing`, realworld and showcase; the showcase client-chunk bundle test covers the generated modules. Docs for Server Services and the new files are updated. These are process requirements, not counted criteria.

## Acceptance Criteria
<!-- scope: both -->

- **R1:** A `*.layer.ts` file whose default export is a Layer is found anywhere in the TS program except tests, and the analyzer composes the found Layers by requirement: a Layer's requirement is provided by another Layer File's output. The composed Layer serves the generated implementation Layers and the explicit `layer` option (which may require what Layer Files provide and wins for any Tag it provides), so a server lists no Layers by hand. Errors: a cycle is `LayerFileCycle`; two Layer Files providing the same Tag are `LayerFileConflict` naming both; a requirement nobody provides is `MissingDependency`; a `*.layer.ts` with no Layer default export, or a default export typed `any`, is `ServerFileShape` naming the file. [paraphrase]
- **R2:** The server directory's `_app.ts` takes the named export `onError` as the error sink; the default stays `console.error`. Errors: any other export is `ServerFileShape` naming the file. [paraphrase]
- **R3:** A `*.rpc.ts` file under the server directory defines one Server Service: each exported function with a written signature is a method (one parameter of any written type or none, a written `Effect.Effect<A, E, R>`, no `any`; accepted forms and `export { x as delete }` as in API Contracts). The Tag is the PascalCase file basename, or the `service` export. The build generates one Tag object per service, the registry entry, the implementation Layer and the browser client; the wire id is `<Service>.<method>` at `POST /_sleek/fn/<id>`; pages call `yield* <Service>` with the Tag imported from `virtual:sleek/rpc`. The names `wrap`, `bodyLimit`, `origins` and `service` are options, not methods. The RPC File inherits `bodyLimit` and `origins` from Directory Defaults, not `wrap`. Errors: a missing signature, `any`, more than one parameter, an unsupported form, or an `R` that names another generated Tag is `RpcMethodShape`; a `service` or derived name outside `[A-Za-z][A-Za-z0-9]*`, or a `service` that is not a string literal, is `ServerFileShape`. [paraphrase]
- **R4:** RPC File methods and wrapped Controller Methods get their Schemas from the signature through the one reader: `Schema.Schema.Type<typeof X>` references use `X`; other types are printed from ADR 0051's subset, with `Schema.TaggedError` classes and string-keyed records accepted as in ADR 0052; `R` may be any service. Errors: a type outside the subset is `ServerServiceTypeNotSerializable`. [paraphrase]
- **R5:** The server directory's `rpc.ts` wraps Controller Methods as Server Services: its default export is an object literal of string literals mapping each Service name to `{ method: 'VERB route-name' }`, with route names typed from the generated route table so renaming a Controller is a type error. A wrapped method needs a written-out signature. The generated Tag, registry entry and client are the same as an RPC File's, and the input is the Controller's `{ params?, query?, body? }` (none when the Controller declares none). Errors: an unknown route, a verb the Controller does not export, or a method that was removed is `RpcRouteUnknown`; a method that returns `Response`, has no written signature or uses `any` is `RpcMethodShape`, reported once; a Manifest that is not an object literal of string literals is `ServerFileShape`. [paraphrase]
- **R6:** The RPC face of a wrapped method decodes the wire input and runs the method inside the Manifest's own `wrap` (an `RpcWrap`), never the Controller directory's `wrap`; typed errors cross the wire as the Exit failure and not as a `Response`; `ResponseStatus` has no effect. The `wrap` and the split of request services from build-time services live in the generated Layer's methods, so wire calls, in-process calls from loaders and `callService` all run inside it. Errors: with no `wrap`, the method's own services still resolve in the Request Scope; an undeclared failure is the error sink and an empty 500. [paraphrase]
- **R7:** Tag names from RPC Files, Manifest keys, hand-written `ServerService` ids, Layer File output Tag keys and `serverFn` ids share one namespace. Errors: a collision is `RpcNameCollision` naming both sources. [paraphrase]
- **R8:** Hand-written `ServerService` with `implement`, `serverFn` with `start({ functions })` and `callService` keep working beside generated services and are unchanged. The registry holds hand-written and generated entries, and `start` de-duplicates `services` by Tag, so passing the registry beside the discovered app registers nothing twice. Errors: no error surface beyond R7. [paraphrase]
- **R9:** The analyzer's one server-only list gains `*.rpc.ts`, `*.layer.ts` and, under the server directory, `rpc.ts` and `_app.ts`; none may be reachable from a browser entry, and `virtual:sleek/rpc` counts as a browser-entry marker. A Schema or error class that a generated client imports must live in a client-safe module: declaring one inside the RPC File or Controller itself, or importing one from a server-only module, is reported. Errors: `ServerFileInClientGraph` naming the chain.
- **R10:** Realworld's three Server Services (identity, articles, comments) are RPC Files named `identity-api.rpc.ts`, `articles-api.rpc.ts` and `comments-api.rpc.ts`, so the Tags and the wire ids stay `IdentityApi.*`, `ArticlesApi.*` and `CommentsApi.*`. Their contracts, `implement` calls and `*Live` Layers are gone; `DbLive(...)`, `TokenSecretLive` and `ServerQueriesLive` are Layer Files (the browser's `AppLive` and `QueriesLive` stay hand-written); helpers such as `asViewer`, `signIn` and `secure`, and the `SESSION` constant, move to a non-RPC server module; pages and tests import the generated Tags from `virtual:sleek/rpc`. REST token auth and the cookie session stay two surfaces. Realworld's architecture test allows `virtual:sleek/rpc` in `pages/`, `routes/` and module presentation and still rejects server-only imports in pages, and its client-chunk test includes the discovery plugin. Errors: every existing page and server test passes with only import changes.
- **R11:** Showcase's `Tally` is a Controller plus the RPC Manifest: `GET` and `POST /api/tally` answer bare numbers, the page calls the generated Tag with `{ body: { by } }`, the wire id stays `Tally.add`, and the declared `TallyLimit` (kept client-safe) still arrives typed. The tally's `Ref` lives in a Layer File, so both faces share it; the REST answer for a past-limit `by` is 409 with `{ limit }`, mapped by a showcase `_defaults.ts` `wrap`. Showcase's dev server forwards Controller paths, and its server tests and client-chunk bundle test pass with the new input shape. Errors: a `by` past the limit fails with `TallyLimit`, as today.
- **R12:** Layer Files, the Server Root, RPC Files and the Manifest are discovered in dev, in build and under vitest like the sibling spec's Controllers: a file added, removed, renamed or edited is picked up without a restart; the new virtual modules are invalidated with it; the declaration's services and methods are sorted and a stale declaration fails `vite build`. Errors: an invalid file leaves the previous declaration in place and the module load reports the file's path.
- **R13:** `origins` exports from RPC Files, the Manifest and `_defaults.ts` only add to the app-wide allow-list, so no file narrows it; `bodyLimit` resolves per service by specificity (the file's own export, then the nearest `_defaults.ts`, then `start({ bodyLimit })`, then 1 MiB) with the wire's order of checks unchanged: method, origin, registered id, body size. Errors: an origin outside the grammar fails `start` with `InvalidOrigin` as today; a `bodyLimit` that is not a positive finite integer fails the app load naming the file.

## Boundaries

- "in case of an RPC need we define it in an .rpc file" [user]
- "try an rpc.ts file seperately to just wrap the controllers for RPC instead of defining manually but keep the .rpc files" [user]
- Out of scope: a production server build and adapters, no-JS form posts to Controllers, OpenAPI output, endpoint clients, streaming results. [paraphrase]
- Unchanged: the `/_sleek/fn` wire, `serverFn` and `start({ functions })`, hand-registered `handlers`. [paraphrase]
- Not built: a `.contract.ts` file kind; wiring from a `*.schema.ts` file (a Schema File is a client-safe naming convention only); a per-directory manifest or an RPC export inside a Controller; path-derived service ids; collapsing the REST facade and the app's Server Services into one surface; per-service `origins` scoping; request-scoped Layer Files. [paraphrase]

## Decision Context
<!-- scope: both — conditionally substructured -->

Why this approach over the alternatives. The wiring that remains after Controllers is Layers, contracts and the service registry; each is either found by extension or generated from a written signature.

- "try an rpc.ts file seperately to just wrap the controllers for RPC instead of defining manually" [user]
- The wrapped RPC face runs the method under the Manifest's own `wrap`: the directory `wrap` reads `Authorization` and turns failures into responses, so a cookie user would be anonymous and typed errors would be lost, and a REST route accepting the cookie would skip the RPC wire's origin check. [paraphrase]
- Signatures must be written out for generated services: an inferred success type is whatever the body returns, so a row with a hash field would be sent. [paraphrase]
- Rejected, one line each: contract-first only (it keeps the second file); a Controller that derives a Server Service for every method (two faces, different auth and errors); a per-directory manifest (method names cannot come from a path and a verb); path-derived service ids (moving a file would break the wire id); `import.meta.glob` (loosely typed, invisible to the analyzer); CLI-generated runtime source (ADR 0045 keeps generation types-only). [paraphrase]
- Plan-time decisions beyond the capture, to be confirmed at plan review: `LayerFileConflict` as a diagnostic and `ServerFileShape` as the shape code; Layer Files found anywhere except tests, RPC Files and reserved files under the server directory; the explicit `layer` wins over Layer Files; `RpcWrap` is type-preserving and the directory `wrap` is never inherited by RPC; `wrap` runs inside the generated Layer's methods (so in-process calls are wrapped); `origins` only adds and is app-wide; `services` de-duplicate by Tag; PascalCase naming and the realworld file names that keep wire ids; Tag-name namespace includes Layer File keys and `serverFn` ids; showcase's 409 mapping for `TallyLimit` and its Layer File for the tally state.
