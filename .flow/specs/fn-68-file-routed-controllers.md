## Goal & Context
<!-- scope: business -->
<!-- Source-tag breakdown: 15% [user] / 60% [paraphrase] / 25% plan-time decisions (listed in Decision Context) -->

Server parts are wired by hand today. `start` takes handlers by exact pathname only (no params), Layers, middleware and a generated registry as separate options. Realworld's REST facade is one 19-entry regex table in one middleware that also decodes each body, resolves the viewer and maps errors by hand, because nothing types a handler's input or output.

The idea behind this spec, in the user's words: "fs routing for server, and extensions based auto wiring so no wiring would be needed". This spec delivers the routing half and the discovery core. A file under the server routes directory is a **Controller**: its path sets its URL, its exported HTTP methods are plain Effect functions typed by their written-out signature, and `start()` serves the discovered Controllers with no wiring. There is no wrapper function around a method.

Target: developers writing a `@sleekstack/start` server who want REST routes without a hand-kept route table. The proving ground is realworld's REST facade.

Design record: ADR 0053 (Controllers) and ADR 0054 (discovery, completed by the sibling spec "Server auto-wiring", which depends on this one). Vocabulary: CONTEXT.md (Controller, Controller Method, Directory Defaults).

## Architecture & Data Models
<!-- scope: technical -->

- **Discovery.** The standalone `serverServices()` plugin of `@sleekstack/ui-vite` (also part of `sleekstack()`) finds Controllers and Directory Defaults files and serves the discovered app as the virtual module `virtual:sleek/server-app`, with a types-only declaration in the existing server declaration file (ADR 0045's rule: no generated runtime code). One writer owns that declaration file, so an invalid Controller never erases the Server Services section. Recognition lives in `@sleekstack/analyze`; the plugin and `sleekstack check` both call it, as ADR 0051 does for Server Services.
- **Routing.** The URL syntax and match order are ADR 0050's. The Controller matcher follows them with one difference from the page matcher: a segment with a malformed percent-escape matches only a `:param`, `:param?` or `*splat` position, whose value then fails to decode (R15), instead of matching no route. The plugin's sort of Controllers is the single source of match order. A request reaches, in order: middleware, server functions and Server Service methods, an exact-pathname handler, a Controller, then the page router.
- **A Controller Method** is a function of one input object `{ params?, query?, body? }` returning `Effect<A, E, R>`. The HTTP face of one method is: `wrap` around (check content type, read the body within its limit, decode input, run the method, encode the answer). Decode and encode Schemas come from the written-out annotation.
- **Request Scope.** `Request`, `Cookies`, `ResponseHeaders` and the new `ResponseStatus` are provided per call; a method shapes the answer through them.
- **Directory Defaults.** A `_defaults.ts` file under the server directory carries inherited options (`wrap`, `bodyLimit`, `origins`) for every Controller below it.
- **Discovered app.** The module carries the Controller entries (route pattern, methods, Schemas, option chain) and, when file routes exist and no explicit `router` is given, the page router built from them. Its entry type is defined in `@sleekstack/start` and consumed by the sibling spec's RPC Manifest.
- **Seam with the sibling spec.** Discovery, the server-only boundary list, the entry type and the signature reader are built here and extended there (Layer Files, RPC Files, the RPC Manifest).

## API Contracts
<!-- scope: technical -->

- **Controller Method:** named export `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE` or `OPTIONS` (matched case-sensitively; the request method is upper-cased); one parameter `{ params?, query?, body? }`, or none; returns `Effect<A, E, R>`; `R` is any service provided by the discovered Layers, the explicit `layer` option or a `wrap`.
- **Input Schema reading:** `Schema.Schema.Type<typeof X>` (inline, or through a type alias in the same file) with `X` an exported Schema value of a client-safe module uses `X`, at any position of a written type (a property, an array element, a union member); any other written type is printed to a Schema from ADR 0051's subset.
- **Answers:** value → JSON 200 (`void` → 204; 204, 205 and 304 carry no body, R16); with a written success type the value is encoded through its Schema; with none it is serialized as it is; a method with no written success type may return a `Response`.
- **`ResponseStatus`:** `ResponseStatus.set(n)` per call; default 200 or 204; a value that is not an integer from 200 to 599 is a defect (`InvalidStatus`). Read only by the Controller HTTP face.
- **`wrap`:** `export const wrap: Wrap`, an authoring type exported by `@sleekstack/start`, `(next: Effect<Response, E, R>, request: Request) => Effect<Response, E2, R2>`. `Redirect` and `NotFound` are control flow: they appear in `E` and, unhandled, answer 302 and 404 as in ADR 0039.
- **Option exports** (Controller file or `_defaults.ts`): `wrap` (Controllers only), `bodyLimit` (bytes, a positive finite integer, default 1 MiB), `origins` (RPC wire only; only adds to the allow-list).
- **Failures that reach `wrap` (R15, R17):** `ParseError` (decode, issue paths relative to the input object such as `params.id` or `body.user.email`), `InvalidPathEncoding`, `MethodNotAllowed` (carries the allowed methods), `BodyTooLarge`, `UnsupportedMediaType`. **Unhandled:** decode failure → 400 with the `DecodeError` JSON; `InvalidPathEncoding` → 404 with no body; `MethodNotAllowed` → 405 with `Allow`; `BodyTooLarge` → 413; `UnsupportedMediaType` → 415; any other failure → error sink and empty 500.
- **`start`:** `router` becomes optional; `start()` with no arguments serves the discovered app; explicit options merge with it.
- **Diagnostics** (closed `AnalyzeCode` union, each with its table row): `ControllerMethodShape`, `ControllerParamsMismatch`; `ServerServiceTypeNotSerializable` is reworded to cover Controller types; `ServerFileInClientGraph` covers the new server-only kinds.
- **Testing:** `callController(entry, request, { layer, onError? })` in `@sleekstack/testing`, resolving to a `Response` (R13).

## Edge Cases & Constraints
<!-- scope: technical -->

- The analyzer reads the annotation syntactically, because `Schema.Type<typeof X>` resolves to a structural type that no longer names `X`; an unusual form fails with a diagnostic and never silently degrades. A `typeof X` whose `X` is not exported or sits in a server-only module is a diagnostic, not a printed type.
- A plain TS annotation is exactly as strict as its type: `name: string` accepts the empty string. A constraint such as `NonEmptyString` needs a referenced Schema. A written type outside the subset (`Date`, `Map`, `unknown`, an intersection) is `ServerServiceTypeNotSerializable`.
- Dropping the return annotation turns encoding off: the value is serialized as it is and extra fields are sent.
- A splat matches one or more segments (ADR 0050), so `/api` itself needs an `index` Controller beside an `api/[...rest]` catch-all; a trailing slash is ignored and an empty segment (`/api//x`) matches nothing.
- Decode rules: a repeated query key gives an array when the annotated type is an array and the last value otherwise; a printed `number` codec accepts a finite decimal only (no `NaN`, `Infinity`, hex or exponent); a printed `boolean` codec accepts `true` and `false` only; `[[id]]` is an optional string; a splat is one string joined with `/`; extra keys are ignored; `body` is legal on `POST`, `PUT`, `PATCH` and `DELETE` only; an empty body with `body` declared is a decode failure; a referenced Schema for `params` or `query` must encode to strings (or arrays of strings for `query`).
- Check order for one call: method (`MethodNotAllowed`), path escapes (`InvalidPathEncoding`), content type (`UnsupportedMediaType`), body size (`BodyTooLarge`), JSON parse, then decode of `params`, `query` and `body` with all issues reported.
- `bodyLimit` applies only when `body` is declared; a method that reads `Request` itself has no limit. A method that declares no `body` leaves the body unread and may read it through `Request`.
- `HEAD` drops the body and is outermost, so an error body built by `wrap` never reaches a `HEAD` answer; a streaming `Response` body is cancelled. The default `OPTIONS` answer and the default 405 run inside `wrap`.
- `ResponseHeaders` and `Set-Cookie` staged before a failure still ride onto the error answer, as ADR 0039 keeps them on a 500; only the status is dropped (R7). A returned `Response` keeps its own status and body; `ResponseStatus` is ignored for it.
- `start()` with nothing discovered and no explicit options fails on the first request with a message naming the missing plugin. Auto-wiring needs Vite; a host without it passes explicit options.
- Reaching a virtual module from a package that Vite may externalize is unverified. The first task settles it in three contexts: `ssrLoadModule`, vitest and `vite build --ssr`, with `start` as a workspace link. It picks between zero-argument `start()` and an app passed in (`start(app)`), and the fallback is that the plugin emits one module that calls `start` and the server entry re-exports it. Virtual-module exports are read only inside functions, never at module top level.
- Matching, routing failures and `callController` tests run serially: `serve()` reconfigures the process-wide runtime on each call.
- The explicit `layer` option stays required in this spec for any service the Controllers need; Layer Files arrive in the sibling spec.
- Verification follows the repo's verify table for analyzer, router, `ui-vite`, `start`, `testing` and realworld, plus the fixture graph check for any public export change. Docs describing server routes are updated. These are process requirements, not counted criteria.

## Acceptance Criteria
<!-- scope: both -->

- **R1:** A `*.controller.ts` file under the server routes directory (default `server/routes`, overridable by a plugin option) is served at the URL its path sets, with the page route syntax and match order: `[id]`, `[[id]]`, `[...rest]`, `(group)` and `index`; files and directories starting with `_` are not routes; static before `:param` before `:param?` before `*splat`. A Controller's route name is its path under that directory without the `.controller.ts` suffix, keeping `(group)` and `index` as page route names do. Errors: an optional or splat segment that is not last fails the build naming the file; a `*.controller.ts` outside the routes directory fails the build naming the file; a path no Controller matches falls through to the page router. [paraphrase]
- **R2:** Two Controllers whose paths differ only in param names, and a Controller and a page route with the same path, fail the build naming both files (the discovery scan reads the page routes and compares with param names ignored). A Controller whose URL would start with `/_sleek/` fails the build. An exact-pathname `start({ handlers })` entry wins over a Controller, and a Controller wins over the page router. A Controller on a more general path shadows a page only for the methods it serves, and answers 405 for the rest: no fall-through to a page is built. Errors: the build failure names both files (no error surface beyond that).
- **R3:** A Controller Method is a plain named export (`GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`) taking one input object `{ params?, query?, body? }` or none, and returning `Effect<A, E, R>`; no wrapper function exists or is required. `R` may be any service, provided by the discovered Layers, the explicit `layer` option or a `wrap`. Errors: a requirement nobody provides is reported by `sleekstack check` as `MissingDependency`, where the services a `wrap` discharges (its `next` requirements minus its result's) count as provided for the Controllers under it, and discovered Controllers are roots for the check even in an app with no ui trees; an export that is neither a method name nor an option export is not served, and a near-miss name (`get`, `Post`, `export default`) is `ControllerMethodShape`. [paraphrase]
- **R4:** Before the method runs, the input is decoded from the written-out annotation: `params` from the path, `query` from the URL, `body` from JSON. A type written `Schema.Schema.Type<typeof X>` (inline or via a same-file alias, at any position) where `X` is an exported Schema value of a client-safe module uses `X` itself; any other written type is printed to a Schema from the Server Service type subset; path and query values are strings, so a printed `number` or `boolean` gets a string codec on the HTTP face only. The keys of `params` must equal the path's params. Errors: an unreadable form, `any`, more than one parameter, an unknown input key, `body` on a method that cannot have one, a `typeof X` that is not exported or not client-safe, or a referenced `params` or `query` Schema that does not encode to strings is `ControllerMethodShape`; a `params` key mismatch (including a missing `params` on a parameterized path) is `ControllerParamsMismatch`; a type outside the subset is `ServerServiceTypeNotSerializable`; a failed decode reaches `wrap` as a `ParseError`, and malformed JSON is a `ParseError` with the message `is not valid JSON`; unhandled, either answers 400 with the `DecodeError` JSON. [paraphrase]
- **R5:** A returned value answers as JSON 200 (204 for `void`; the null-body statuses are R16). When the success type is written out, the value is encoded through its Schema, so fields outside it are not sent; without a written success type it is serialized as it is. A method with no written success type may return a `Response`, which passes through untouched with its own status and body. `null` answers as JSON `null`. Errors: an encode failure or any other unhandled failure is a defect: the error sink and an empty 500.
- **R6:** A method reads and shapes the request through request services in the Request Scope: `Request`, `Cookies`, `ResponseHeaders` and a new `ResponseStatus` (`ResponseStatus.set(n)`; default 200, 204 for `void`). `ResponseStatus` joins the request-services type, so a Server Service implementation may use it; it is read only by the Controller HTTP face and has no effect on the `/_sleek/fn` wire or in any other stage. Two concurrent requests setting different statuses never see each other's. Errors: no error surface beyond R7. [paraphrase]
- **R7:** `ResponseStatus.set` dies with `InvalidStatus` for a value that is not an integer from 200 to 599 (a programmer error, so `E` stays clean). A method that sets a status and then fails answers with the status `wrap` gives the failure, and the earlier value is dropped; staged `ResponseHeaders` and `Set-Cookie` lines still apply to the error answer. Errors: as stated.
- **R8:** A `_defaults.ts` file in a directory under the server directory takes the option exports `wrap`, `bodyLimit` and `origins` and applies to every Controller below it; a Controller may export the same options. `wrap(next, request)` receives the HTTP face's Effect (decode, method, encode), provides services such as the viewer, and maps failures to responses; it composes outer first. `bodyLimit` resolves by specificity: the Controller's own export, then the nearest `_defaults.ts`, then `start({ bodyLimit })`, then the default (1 MiB); it applies only when `body` is declared. `origins` only adds: the app-wide allow-list for the RPC wire is the union of `start({ origins })` and every `origins` export, and no file can remove an origin. Errors: a body over `bodyLimit` fails with `BodyTooLarge`, which reaches `wrap` and, unhandled, answers 413; a `bodyLimit` that is not a positive finite integer fails the app load naming the file. [paraphrase]
- **R9:** `HEAD` runs `GET` and drops the body unless the file exports `HEAD`; `OPTIONS` answers 204 with `Allow` unless exported; an unsupported method is `MethodNotAllowed` (R15). `Allow` is the served methods in canonical order, with the implicit `HEAD` and `OPTIONS` listed. No CORS headers are sent by default (the app sets them in `wrap` through `ResponseHeaders`). Errors: `HEAD` with no `GET` is `MethodNotAllowed`; no other error surface beyond R15. [paraphrase]
- **R10:** The standalone `serverServices()` plugin (also part of `sleekstack()`; options `serverDir`, default `server`, and `controllersDir`, default `<serverDir>/routes`) finds Controllers and `_defaults.ts`, serves the discovered app as a virtual module, and writes a types-only declaration into the existing server declaration file through one writer; recognition lives in `@sleekstack/analyze`, called by the plugin and by `sleekstack check`. The discovered app also gives a dev server what it needs to forward Controller paths to `start`, so an app's dev server hard-codes no `/api/`-style prefix. In dev a Controller or `_defaults.ts` added, removed, renamed or edited (body or annotation) is picked up without a restart, and a `_defaults.ts` change re-resolves every Controller beneath it. "Works in build" means the client build excludes Controllers and an SSR build entry resolves the module. Errors: an invalid file leaves the previous declaration in place and the module load reports the file's path.
- **R11:** `start()` takes no arguments and serves the discovered app: the Controllers and, when file routes exist and no explicit `router` is given, the page router built from them. `router` becomes optional (an app with neither serves 404 for pages). Explicit options still work and merge with the discovered ones: arrays concatenate (`services` are de-duplicated by Tag identity, so passing the generated registry beside the discovered app registers nothing twice; a repeated `serverFn` id stays a `DuplicateServerFn` error), Layers merge with `Layer.provideMerge`, and an explicit global scalar (`onError`, `bodyLimit`) is the default beneath the specificity order of R8. Errors: a call with nothing discovered and no explicit options fails on the first request naming the missing plugin.
- **R12:** `*.controller.ts` and `_defaults.ts` (under the server directory) are server-only: none may be reachable from a browser entry, and the analyzer holds one list of server-only kinds, shared with the plugin, that the sibling spec extends. Errors: the Vite load hook fails the client build naming the chain, and `sleekstack check` reports `ServerFileInClientGraph` for the browser entries it can identify.
- **R13:** `@sleekstack/testing` gains `callController(entry, request, { layer, onError? })`, shaped like `callHandler`. `entry` is the Controller's generated entry from the discovered app module, typed by route name; it carries the Schemas and option exports that the erased annotations cannot. It matches `request`'s URL against the entry's pattern (a mismatch answers 404) and resolves to the `Response` the HTTP face gives (content-type check, decode, the directory `wrap` chain, encode and the R9 defaults included), skipping middleware and server functions, with a test Layer and no network. Errors: a failed decode resolves to whatever `wrap` maps it to, else the 400 `DecodeError` JSON; a defect is an empty 500 and its cause goes to `onError`; a test with a referenced Schema checks parity with `start(...).fetch`.
- **R14:** Realworld's REST facade is served by Controllers: its regex-table middleware is gone; a directory `_defaults.ts` provides the viewer from `Authorization: Token` and maps the tagged errors, `InvalidPathEncoding`, `MethodNotAllowed`, `BodyTooLarge` and decode failures to the RealWorld statuses and `{errors}` bodies (a failed `params` decode answers 404, a failed `body` decode answers 422 with field paths relative to the body, malformed JSON keeps `is not valid JSON`, an over-limit body keeps `is too large`); `index` and `[...rest]` Controllers answer `/api/` and an unknown `/api/` path with the JSON 404. The existing REST tests pass, including the cases for an unknown route, an unsupported method and a malformed percent-escape; the only edits are `Content-Type: application/json` on the two size-limit requests (R17 checks the media type before the size), whose 413 assertions stay, plus a separate 415 test. Intended differences from today: an invalid token on an unknown route, unsupported method or malformed escape answers 401 (routing now runs inside the directory `wrap`); `/api/articles/` answers like `/api/articles`; `/api//x` and other paths with an empty segment reach the page router. Errors: 401 for a bad token, 404 for an unknown path, a malformed escape, a non-numeric comment id or an unsupported method, 413 for a body over the limit, 415 for a body without `application/json`, 422 with field errors for a failed body decode.
- **R15:** Routing failures reach `wrap` as failures, like a decode failure. A malformed percent-escape in a path segment matches only a `:param`, `:param?` or `*splat` position and fails the call with `InvalidPathEncoding` when that value is decoded. A path that matches a Controller but not its method fails with `MethodNotAllowed`, carrying the allowed methods, before any decode; the R9 `HEAD` and `OPTIONS` defaults apply first. Unhandled, `InvalidPathEncoding` answers 404 with no body and `MethodNotAllowed` answers 405 with `Allow`. Errors: a malformed escape in a static position matches no Controller and falls through to the page router.
- **R16:** A status of 204, 205 or 304 carries no body: a value returned with one of them is not sent and the status is kept; `undefined` sends an empty body at any status; every other status from 200 to 599 sends the JSON value. Each of the three null-body statuses is tested through `fetch`. Errors: no error surface beyond R7.
- **R17:** A method that declares `body` requires `Content-Type: application/json` (a charset parameter is accepted); a request without it fails with `UnsupportedMediaType`, delivered to `wrap` and, unhandled, answering 415. This closes cross-site form posts (`text/plain`, form-urlencoded) to cookie-authenticated Controllers without an origin check. Errors: no error surface beyond the 415.

## Decision Context
<!-- scope: both — conditionally substructured -->

Why this approach over the alternatives. Routes are REST by default and RPC is opt-in, so a Controller needs no contract; types come from the written signature and request-scoped effects replace option exports.

- "a schema file doesn't need the wrappers just export default a schema, and controller methods can simply cast the param/body types with Schema type" [user]
- "also we can leverage Request scoped effects" [user]
- Status, headers and cookies are therefore request services, and there is no `status` option export. [paraphrase]
- With the helper, the Schemas sat in a server-only file that the browser client generated for RPC cannot import; stripping that file in the client build rests on import pruning, which ADR 0051 rejected. The annotation carries the same information without it. [paraphrase]
- Rejected, one line each: a keyed `schema` export or a sibling Schema File paired by name; decoding in the body with a cast (it can lie, and the RPC wire needs a Schema value at run time); a `status` option export or a returned `Response` for the status (a `Response` cannot cross the RPC wire); Controllers beside pages (the page scan takes every `.ts` file there and `src` is the client graph); class controllers; a Controller that is also a Server Service by default (two faces with different auth and error shapes). [paraphrase]
- Plan-time decisions beyond the capture, to be confirmed at plan review: an explicit handler wins over a Controller; `wrap` composes outer first and the default `OPTIONS` and 405 run inside it; `InvalidStatus` is a defect; decode failures default to 400; the page router is discovered from file routes when none is given; `Content-Type: application/json` is required for bodies (415); body-size and malformed-JSON failures reach `wrap`; routing failures reach `wrap` and an invalid token on an unknown route answers 401 in realworld; `bodyLimit` resolves by specificity while `origins` only adds (a file can never narrow the allow-list); `wrap` from `_defaults.ts` covers Controllers only; `services` merge by Tag identity; plugin options `serverDir` and `controllersDir`; the `callController` contract (entry from the discovered module, `Response` result).
- Maintainability (plan review): duplication - tasks 9 and 12 both assigned the `callController` documentation update in the testing docs page (now owned by task 12); structure - none identified
